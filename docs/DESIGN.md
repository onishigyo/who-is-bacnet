# BACnet 学習アプリ 設計ドキュメント

> このドキュメントは、BACnet/IP・BACnet/SC の仕組みと危険性を体験的に学べる Web アプリの設計を定義する。実装（Claude Code）に渡す前提で、「何を・誰に・どう伝えるか」と「どう作るか」を記述する。

---

## 1. このアプリは何か

### 一言で

BACnet（ビル設備の制御プロトコル）が、**同じネットワークにいるだけで認証なしに操作できてしまう**という事実を、ネットワーク図の上で「体験」させ、その解決策である BACnet/SC までを理解させる、インタラクティブな学習教材。

### 生まれた背景

書籍『2025-2035 サイバー空間の地政学』の一節（攻撃される前提に立つ防御思想）をきっかけに、建築設備のネットワークがほとんど守られていない実態への問題意識から出発。実際に Kali Linux と Ubuntu で BACnet/IP・BACnet/SC の通信を発生させ、Wireshark でパケットを検証した実験の成果を、教材として結晶化する。

### 何を「本物」で担保するか

- インタラクティブUI（ネットワーク図・パケットアニメーション）は「それっぽく動く」再現。ブラウザ内で完結し、**実際の BACnet 通信は発生させない**（公開型でバックエンドを持つのはインフラ・セキュリティ上の負荷が過大なため見送り）。
- 「本物である」ことの担保は、**実験で実際に取得した Wireshark キャプチャ（pcapng / スクリーンショット）を各ステップの答え合わせとして提示する**ことで果たす。

## 2. 対象ユーザーと届けたいこと

### 中心メッセージ

> **BACnet/IP は、同じネットワークにいるだけで、認証なしに設備を操作できてしまう。その恐ろしさを体感し、BACnet/SC という解決策と、その限界までを理解する。**

### 学習の順序（重要な設計判断）

危険性から入らない。まず対象を理解・共感させてから、その足元にある落とし穴を見せる。

1. BACnet ってこういうもの（何者か）
2. BACnet/IP ってこういうもの（IP ネットワークで動く BACnet）
3. こういう便利な側面がある（なぜ普及したか）
4. だけど、こういう危険性がある（無認証・丸見え・書き換え可能）

いきなり「危ない!」から入る教材は「自分には関係ない怖い話」で終わりがち。この順序により、危険性が **自分ごと** になる。

## 3. 体験設計：方向B「1つの世界を育て、最後に壊す」

### 基本方針

**全ステップを通して、1つのネットワーク図を舞台にする。** 図に要素を段階的に足していき（機器が増える → IP がつく → 中央監視が繋がる）、最後のステップでその平和な世界に「攻撃者」が現れる。利用者が理解し馴染んだ世界が壊されることで、当事者感が生まれる。

（対案として「前半は読み物、後半だけインタラクティブ」も検討したが、前半と後半が分断されるため不採用。同じ図を育てる一貫性を優先する。）

### 各ステップの図の状態

| ステップ                       | 図の状態                                                                                                                             | 伝えること                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| **1. BACnet とは**             | ノードが1つ「BACnet機器（空調コントローラ）」がぽつんと存在                                                                          | 設備機器が会話するための共通言語。まだ孤立。ここでは IP の話はしない |
| **2. BACnet/IP とは**          | その機器に IP アドレス（192.168.x.x）の札がつき、ネットワーク線が引かれる                                                            | BACnet を普通の IP ネットワーク上で喋れるようにしたもの              |
| **3. 便利な側面 + 実際の会話** | 機器が増え、中央監視装置が繋がる。異なるメーカーの機器も同じネットワークに並ぶ。**中央監視とデバイスの間で「会話」が吹き出しで飛ぶ** | BACnet はこういう親切な会話で動いている（＝正常な運用）              |
| **4. 危険性**                  | その平和なネットワークに、突然「攻撃者」ノードが現れる。利用者が攻撃者を操作                                                         | 認証が一切ないから、攻撃者も同じ言葉で割り込める（＝危険性）         |

### 「会話」の見せ方（このアプリの核心）

ステップ3で「正常な会話」を見せ、ステップ4で「攻撃の会話」を見せる。**両者は見た目上まったく同じ通信**であり、話し手が「中央監視」から「攻撃者」に変わるだけ。この対比が、無認証という弱点の本質を突く。

**正常な運用（ステップ3）**

```
[中央監視] ──「室温を教えて」──→ [空調機器]
[中央監視] ←──「22.0℃です」──── [空調機器]
```

**攻撃（ステップ4）**

```
[攻撃者]   ──「設定温度を99℃にして」──→ [空調機器]
[空調機器] ←──「了解しました」──────    （認証確認なし!）
```

### 会話の粒度：二層表示（案C）

各メッセージを「意訳」と「実コマンド」の二層で見せ、入門者にも技術者にも刺さるようにする。

| 意訳（初学者向け）        | 実コマンド／プロトコル用語（技術者向け）        |
| ------------------------- | ----------------------------------------------- |
| 誰かいますか?             | `Who-Is`（ブロードキャスト）                    |
| 私はhere、ID 3056930 です | `I-Am device,3056930`                           |
| 室温を教えて              | `ReadProperty analogInput,0 presentValue`       |
| 22.0℃です                 | → `22.0`                                        |
| 設定温度を99℃にして       | `WriteProperty analogValue,0 presentValue 99.0` |
| 了解しました              | → `Simple-ACK`（認証確認なし）                  |

### ステップ4のインタラクション方針

利用者が攻撃者を操作して、Who-Is → 値を読む → 値を書き換える、を実際に試す。各操作の答え合わせに、実験で取得した Wireshark キャプチャ（平文で中身が丸見え）を提示する。

（フルインタラクティブ／ガイド付きのどちらにするかは実装時に決定。初学者比率が高いならガイド付き推奨。）

## 4. BACnet/SC 編（IP 編の完成後に着手）

IP 編と同じネットワーク図・同じUIの仕組みを応用して制作する。

### 伝えること

- BACnet/SC は、証明書（X.509）を持つ機器だけがハブに参加できる（＝参加の可否が証明書だけで決まる）
- 証明書がなければ接続の入り口で拒否される（実験では `CertificateRequired` / `UnknownIssuer` で門前払いを確認済み）
- 通信は TLS 1.3 で暗号化され、Wireshark で見ても中身が読めない

### IP との決定的な対比（Before / After 素材）

実験で取得済みの2つの Wireshark キャプチャを並べる。これがSC編の核心的な見せ場。

|               | Wireshark の Info 欄に見えるもの                                                                    |
| ------------- | --------------------------------------------------------------------------------------------------- |
| **BACnet/IP** | `who-Is`、`readProperty analog-input`、`writeProperty analog-value` ── **何をしているか全部読める** |
| **BACnet/SC** | `Application Data`（暗号化）── **何をしているか全く読めない**                                       |

※「Wireshark で中身が見えない」のは SC の弱点ではなく、盗聴を防ぐという目的の達成そのものである点を、教材として明示する。

### SC のデメリットも扱う（公平性）

- 既存機器の多く（特に古い設備）は証明書に対応できず、全機器の SC 化は現実には困難
- 証明書の運用自体に専門知識が要り、設定ミス（例：証明書の SAN 忘れ）でセキュリティが機能しないリスクがある（実験中に実際に遭遇）
- BACnet/IP と BACnet/SC の混在は、境界が新たな弱点になりうる

## 5. 変換器（ルーター）編（将来・未実験）

IP と SC の境界に置くルーター／ゲートウェイを扱う。**この部分はまだ実験できていない**ため、規格の一次情報に基づく解説を主とし、実装は IP・SC 編の完成後に検討する。

### 扱いたい論点

- SC バックボーンと既存 IP/MS-TP セグメントの間にルーターを置くのが、現実的な導入パターン
- 「中枢（スーパーバイザー↔DDC）だけ SC 化し、末端は既存プロトコルのまま」という段階的アプローチ
- ただし DDC 自体が SC 対応していなければ、その先の IP セグメントは無防備なまま（制作者の手元の実機でも、仕様上 SC に対応していないことを確認済み）
- 末端セグメントに侵入されればそのサブネットは陥落するが、SC 境界を越えて他サブネットには伝播しにくい、という「被害の封じ込め」効果

## 6. 技術スタック

制作者が過去プロダクト（React Flow を用いた SPA を複数）で実績のある構成をそのまま採用する。技術的な習熟コストはほぼゼロ。

- **フレームワーク**: React 19 + TypeScript
- **ビルド**: Vite
- **図の描画**: React Flow（@xyflow/react）── ノード（機器・攻撃者・ハブ）とエッジ（ネットワーク線）、パケットアニメーションの舞台
- **配布**: 静的サイトとして公開（`vite-plugin-singlefile` で単一 HTML 化、または通常の静的ホスティング）
- **ホスティング**: GitHub Pages / Cloudflare Workers（静的アセット）など。**バックエンドを持たない**
- **品質**: TypeScript 型チェック・ESLint・Vitest。純粋ロジック（ステップ状態遷移・会話データの整形など）をテスト対象とする
- **CI/CD**: GitHub Actions（型チェック・Lint・テストを必須チェック、main への push で自動デプロイ）

### 設計原則（過去プロダクトの流儀を踏襲）

- 関心の分離を徹底する。ドメイン型、純粋ロジック（DOM も storage も触らない）、描画・イベント配線を分離する
- ステップの状態遷移と会話データは、UIから独立した純粋ロジックとして持ち、テスト可能にする
- Wireshark キャプチャ画像などの「本物の素材」は `assets/` 配下に置き、各ステップと対応づける

## 7. アセット（実験で取得済みの本物の素材）

| 素材                                                  | 内容                                                        | 使う場所                  |
| ----------------------------------------------------- | ----------------------------------------------------------- | ------------------------- |
| IP 版キャプチャ（`ip_plaintext_traffic.pcapng` 相当） | Who-Is / I-Am / ReadProperty / WriteProperty が平文で見える | ステップ4の答え合わせ     |
| SC 版キャプチャ（`sc_encrypted_traffic.pcapng` 相当） | TLS ハンドシェイク → 暗号化された Application Data          | SC 編の Before/After 対比 |

※ pcapng そのものより、Wireshark で表示したスクリーンショット（Info 欄が読める状態）を教材画像として使うのが現実的。

## 8. 制作の順序

方向性のブレを避けるため、一度に全部作らず、IP 編を完成させてから横展開する。

1. **IP 編（ステップ1〜4）を完成させる** ── 最も素材が揃い、制作者の理解も最も深い。ここでネットワーク図・会話アニメ・Wireshark 答え合わせの「型」を作る
2. **SC 編を追加** ── IP 編の仕組みを応用。証明書による参加可否、Before/After 対比
3. **変換器編を検討** ── 未実験のため、まず解説ベース。必要なら追加実験
